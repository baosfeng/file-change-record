# dsh-guardian 需求清单（设计基准）

> ⚠️ **每次开发本插件的新功能或修复前，必须逐条对照本清单**：新改动不得破坏任何一条既有需求；涉及"失败隔离 / 重启恢复"的需求变更后必须跑回归验证。

## 0. 设计背景（为什么存在这个插件）

DSH（DeepSeek Harness）的 Cordis 插件加载是 **all-or-nothing**：

| 场景 | 当前行为 |
|------|---------|
| 启动时插件 import 失败 | `assertEntriesLoaded` throw → 整个 `dsh web` 启动失败 |
| 启动时插件 apply 抛错 | fail-loud（`unhandledRejection` → 进程 `exit(1)`） |
| 启动时插件 pending（依赖缺失） | `assertEntriesActivated` throw |
| 运行中 HMR 热更新失败 | ✅ 宽容：警告 + `hmr/config-update-failed`，事务回滚旧树 |

关键洞察：**运行时的动态挂载失败是宽容、可 catch、可回滚的**（`EntryTree.create()` reject 不污染 store；`EntryGroup.update()` 失败自动回滚）。只有**启动阶段**是致命的。因此本插件把"新装/刚更新的插件"一律推迟到启动完成之后动态挂载，绕开全有全无窗口。

业界参照：VS Code（Extension Host 独立进程 + 崩溃自动重启 + `--disable-extensions` + 懒激活）、IntelliJ（PluginClassLoader 隔离 + Dynamic Plugins 运行时装卸 + 损坏插件跳过）、systemd（`Restart=on-failure` + 失败超限标记 failed + 依赖分级启动）、OSGi（bundle 加载失败不影响容器）。

## 1. 核心需求

| # | 需求 | 设计/实现 | 验证方式 |
|---|------|----------|---------|
| R1 | **两段式加载**：新插件不进启动加载路径，先入候选区（`cordis.staged.json`），由守护插件在 DSH 启动完成后逐个热挂载 | server `plugins/dsh-guardian/lib/index.js`：boot 后读候选文件 → 对未 disabled 条目调用正式 include 树的 `create()` 动态挂载（经 `@deepseek-ai/cordis-plugin-loader` 的 EntryTree API） | 手动：候选区放一个正常插件 → 重启 DSH → 启动不阻塞、插件随后自动挂载 |
| R2 | **成功自动转正**：候选条目挂载成功后，从候选区移除并保留在正式树（`tree.create` 已持久化进 `cordis.patch.yml`），后续重启直接随正式区启动 | create 成功 → 候选文件写回移除该条 | 手动：转正后重启 DSH，插件仍在运行 |
| R3 | **失败自动隔离**：候选条目挂载失败（import 失败 / apply 抛错 / 依赖缺失）时自动 `tree.update(id, { disabled: true })` 写回正式区（保留行、标记禁用），错误入日志，通知用户 | catch create 的 rejection → 写回 disabled + 状态记录（`$DSH_HOME/guardian/state.json`）+ 可选复用 dsh-notify | 手动：候选区放坏插件 → 挂载失败 → patch 中该行变 disabled: true，UI 显示失败原因 |
| R4 | **连续失败冻结**：同一候选条目连续失败 ≥ 3 次进入 frozen，不再自动重试，需 UI 手动解除 | state.json 记录 attempts，达到阈值置 frozen | 手动：坏插件连续重启 3 次后状态 frozen，自动重试停止 |
| R5 | **安全模式**：开启后所有候选条目跳过加载，正式核心区不受影响；一键恢复被新插件搞坏的环境 | state.json `safeMode: true`；UI 开关 + 文件兑底 | 手动：开安全模式重启 → 候选全部不挂载，正式插件正常 |
| R6 | **运行中增量挂载**：DSH 运行期间新增候选条目自动热挂载（无需重启） | 监听候选文件变更（fs watch + 轮询兑底） | 手动：运行中往候选区加条目 → 自动挂载 |
| R7 | **状态持久化与重启恢复**：guardian 重启后恢复 state.json（失败记录、frozen、safeMode 不丢） | 原子写 + 损坏降级（同 dsh-file-activity 的 loadState 模式） | 重启 DSH → 状态保持 |
| R8 | **诊断面板**：侧边栏（dsh-better-sidebar）新增"插件守护"页签：候选状态列表（待加载/运行中/已禁用/失败×N/冻结）、重试/启用/移除候选/查看错误详情、安全模式开关、全局 loader 条目只读快照 | client `plugins/dsh-guardian/lib/client.js` 复用 dsh-better-sidebar 服务（同 dsh-file-activity 集成模式） | 手动 + `node --check` |
| R9 | **更新失败通知**：监听 `hmr/config-update-failed`，向用户提示"插件更新失败已回滚"（回滚由 include 树事务性 update 天然提供） | ctx.on 监听 + 通知 | 手动触发一次失败更新 |
| R10 | **事件日志**：监听 `loader/entry-init` / `loader/partial-dispose` 记录诊断事件 | 轻量环形日志（内存 + state 摘要） | 手动观察日志 |
| R11 | **id 冲突保护**：候选条目 id 与正式树已有条目冲突时拒绝挂载并提示（防止 `create` 意外覆盖已有 entry） | 挂载前 `tree.resolve(id)` 预检 | 手动构造冲突 |
| R12 | **看门狗自保**：守护插件自身挂载在正式 `cordis.patch.yml` 首行、无 `inject` 硬依赖、代码极薄；自身挂载失败只影响候选加载，不影响核心 | 实现约束 | 代码审查 |
| R13 | **候选文件用 JSON 非 YAML**：守护插件（动态插件代码为纯函数体，不能 `import js-yaml`）用原生 `JSON.parse` 解析 | 候选区格式 `cordis.staged.json`（顶层数组：`{id, name, config, note?}`） | 手动 |
| R14 | **API 安全**：守护插件的 HTTP API（如有）只接受回环/可信 host | 复用 dsh-file-activity 的 `isTrustedApiRequest` 模式 | 手动（fence） |

## 2. 诚实边界（写进文档，不越权承诺）

| 诉求 | 插件层能做到 | 说明 |
|------|------------|------|
| 失败自动禁用 / 逐步加载 / 安全模式 | ✅ | 本插件 |
| 进程级隔离 | ❌ 需 DSH 框架 | server 插件同 Node 进程、client 同浏览器页面；真隔离需 worker_threads/子进程 + RPC（框架演进建议见概述「框架演进方向」） |
| 启动阶段坏插件不拖垮启动 | ❌ 需 DSH 框架 | fail-loud 是 `dsh-app-boot` 的 `assertEntriesActivated` 行为。缓解：核心区只放稳定插件，新插件一律走候选区 |

## 3. 用户明确确认过的设计决策（2026-08-23）

- 产出形态：**治理插件**（不动 DSH 核心）
- 候选区形态：**独立候选文件**（`cordis.staged.json`，非正式 patch 内标记）
- 失败处置：**自动禁用 + 记录 + 通知**（不停下等用户决定）
- 连续失败 3 次冻结，需手动解除
- 诊断面板：**复用 dsh-better-sidebar 侧边栏页签**（与 dsh-file-activity 一致）
