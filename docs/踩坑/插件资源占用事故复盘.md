# 插件资源占用事故复盘与防护调研（issue #127）

> 本文是 issue #127「插件资源占用防护调研」的调研报告：**DSH 运行时资源观测能力盘点 + 高频插件资源热点清单（含 #126 根因）+ 对照 resource-budget-review 五维评审的不足 + 分级整改建议表**。
> 可复用规范与防护机制见 [插件资源安全规范](../开发指南/插件资源安全规范.md)；本 PR 落地的防护清单见文末 [§6](#6-本-pr-落地的防护清单)。

## 1. 事故复盘：#126 根因与现状对照

### 1.1 事故根因（#126，9/2）

事故时 observability v0.1.2 的事件审计实现为：

```
高频监听（agent/status、llm/stream、tools/*）→ 按会话分桶累积
→ 每次防抖落盘：writeFile(tmp, JSON.stringify(全部事件桶))
```

长会话（数小时 agent 编排 + 多子 agent）事件数万条后：

- **CPU**：每次持久化全量序列化巨型嵌套对象（macOS `sample` 显示主线程 566/2070 样本在 `JSON.stringify` 路径），CPU 持续 423%；
- **内存**：序列化中间对象 + 常驻事件桶膨胀，Physical footprint 峰值 4.7G；
- **磁盘**：防抖后仍高频全量重写，几小时内约 300GB 写入。

### 1.2 现状对照（2026-09-04，main 7614b4a）

事故后已在 v0.1.3/v0.1.4 完成两轮修复，**核心写放大根因已消除**：

| 修复项                                                                                                                                      | 落地版本      | 实现位置（源码证据）                                                                                                                                       |
| ------------------------------------------------------------------------------------------------------------------------------------------- | ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 审计持久化改**增量追加**（append-only jsonl + 周期 compact 原子快照 + 旧格式迁移）                                                          | v0.1.3        | `lib/store.js`（enqueueRecord 排队增量行 / flushNow 批量 append）、`lib/store-persist.js`（appendLines 增量 / writeSnapshot compact / COMPACT_LINES=5000） |
| 每会话 2000 / 全局 20000 事件上限（FIFO + 整桶轮转淘汰）                                                                                    | v0.1.2 已有   | `lib/store.js`（appendEvent / evictOldest）                                                                                                                |
| **资源监控看板**：15s 采样 CPU/RSS/审计文件字节/写入速率 + 阈值告警（write-rate 50MB/h、file-size 50MB、cpu 10%、memory 500MB，可配置覆盖） | v0.1.4        | `lib/resource-monitor.js`（createResourceMonitor / sample / ring buffer 60）、`lib/resource-rules.js`（evaluateResourceAlerts / DEFAULT_LIMITS）           |
| 写放大**复现测试**（RED 基线：200 条事件落盘字节 ≤ 事件行字节 ×1.6）+ 资源阈值单测                                                          | v0.1.3/v0.1.4 | `test/host-store.mjs`（'store: 高频事件下持久化为增量追加'）、`test/host-resource.mjs`                                                                     |

### 1.3 仍未覆盖的缺口

对照 #126 复盘四缺口与 #127 期望，**当前仍缺**：

1. **无自动降级路径**（#126 复盘缺口 3 / #127 期望 3）：resource-monitor **只告警不动作**——写入速率连续超限后不会降级（降采样/停落盘/限流），仍需人工介入；
2. **无发版前资源回归门禁**（#126 复盘缺口 2 / #127 期望 2）：CI 无独立资源冒烟 job（现有写放大断言混在 observability 单测中，无「长会话 + 资源上限」形态的冒烟）；
3. **验证清单缺「资源曲线平稳」项**（resource-budget-review skill 要求）：`verification/*.md` 模板无资源观察项，长会话资源曲线平稳无验证入口；
4. **共享原语护栏未默认强制**：`dsh-shared/lib/persist.js` 的 `atomicWriteJson` 的 `maxBytes`/`minIntervalMs` 默认 `Infinity`/`0`（无护栏），调用方不传即裸奔（context/file-activity 现状即未传）；
5. **file-activity 状态上界缺口**：`known`/`counts` 字典无上限（见 §3.3）。

## 2. DSH 运行时资源观测能力盘点

### 2.1 插件进程内可用的观测 API（Node 内置，无需 DSH 支持）

| API                               | 内容                                            | 成本 | 仓库内已用                              |
| --------------------------------- | ----------------------------------------------- | ---- | --------------------------------------- |
| `process.cpuUsage()`              | 进程累计 user+sys CPU（µs），窗口差值换算百分比 | 极低 | observability `lib/resource-monitor.js` |
| `process.memoryUsage().rss`       | 常驻内存字节                                    | 极低 | observability `lib/resource-monitor.js` |
| `fs.stat(file).size`              | 目标文件字节（写放大/存量观测）                 | 极低 | observability（审计文件大小与写入速率） |
| `process.uptime()` / `Date.now()` | 时间窗                                          | 极低 | observability（速率分母）               |

**结论**：插件**无需 DSH 运行时暴露额外 API**，Node 内置能力即可实现进程级 CPU/内存/文件写入观测（observability 已证明，采样开销 <0.01% CPU）。

### 2.2 DSH 运行时是否暴露资源统计

- DSH（`@deepseek-ai/dsh`）**未提供**插件级资源统计 API（无 per-plugin CPU/内存/IO 采样接口）；
- 官方 `session_projcache.json` 写放大案例（见 `AGENTS.md` 关联草稿）：**DSH 核心自身也踩同类坑**——长会话下 `~/.dsh/storages/session_projcache.json` 达 ~74MB 且每 2-4 秒全量重写（write tmp + rename），持续 ~100MB/s 磁盘写入。该案例确认：
  1. 全量序列化 + 原子替换 + 事件级触发 = 灾难组合（与 #126 同模式）；
  2. **插件不能假设运行时自身有资源护栏**——生产实例的资源安全需要插件侧自守（本仓库手柄：规范 + 自监测降级 + 写放大测试）。

### 2.3 仓库内现有观测手段盘点

| 插件                 | 手段                                                 | 形式                                                                        | 状态                           |
| -------------------- | ---------------------------------------------------- | --------------------------------------------------------------------------- | ------------------------------ |
| dsh-my-observability | 事件审计写入速率/文件大小/CPU/RSS 采样 + 阈值告警    | `GET /observability/api/resources` + 面板「资源」区块 + 60 样本 ring buffer | ✅ 已落地 v0.1.4               |
| dsh-my-observability | 写放大定量断言（落盘字节 ≤ 事件字节 ×1.6）           | `test/host-store.mjs`                                                       | ✅ 已落地                      |
| dsh-my-context       | token 统计（每会话 requests ≤500 FIFO + usage 汇总） | `lib/store.js` / `persist.js`                                               | ⚠️ 无资源自监测                |
| dsh-file-activity    | LRU（每会话 recent ≤5 + counts 字典）                | `lib/state.js` / `store.js`                                                 | ⚠️ 无资源自监测，counts 无上限 |
| dsh-shared           | `atomicWriteJson` 护栏参数（minIntervalMs/maxBytes） | `lib/persist.js`                                                            | ⚠️ 默认无护栏，调用方需显式传  |

## 3. 高频写路径热点清单

### 3.1 observability 审计（#126 根因，已修复）— 低风险（需补降级）

- **写模式**：事件流型 → 增量 append + compact（正确原语）✅
- **触发频率**：agent 状态 / 流 chunk / 工具调用每事件一条
- **内存上界**：每会话 2000 / 全局 20000（FIFO）✅
- **写放大**：≤1.x（有断言）✅
- **剩余风险**：写放大被正确原语压制后，**剩余风险转为 CPU/内存峰值**（事件数上限 20000，单次 stringify 一行的成本仍随事件对象大小增长——参数摘要已截断键列表 ≤10 / 文本 ≤200 字符，风险有限）；**无自动降级路径**（写入速率连续超限时只告警）。

### 3.2 dsh-my-context 统计 — 中风险

- **写模式**：状态快照型 → `atomicWriteJson` **全量重写** + 防抖 500ms
- **触发频率**：每轮 LLM 请求（`recordRequest`）+ 消息/头更新（`updateHeader`/`addMessage`/`startTurn`）均触发 `persistSoon`
- **状态大小**：每会话 requests ≤500 + alerts ≤50 + overflows ≤50 + usage/composition 汇总；**会话数无上限**（每个新 sessionId 新增桶，长会话+多子 agent 会话数可达数十）
- **写放大估算**：单请求记录 ~300B，500 条/会话 ≈ 150KB；10 会话 ≈ 1.5MB。每次变更全量序列化 1.5MB → 若每 1-2s 变更一次 ≈ **3.6-7.2 GB/小时**（低于事故量级但在同一模式上）
- **风险点**：全量重写（非增量）+ 无字节护栏（`atomicWriteJson` 未传 `maxBytes`）+ 无资源自监测
- **缓解现实性**：状态是汇总统计（非事件流），改 append 不自然；正确做法是**节流窗口 + 字节上限 + 会话数上限**（见整改表）

### 3.3 dsh-file-activity LRU — 中-高风险（触发最高频）

- **写模式**：状态快照型 → `atomicWriteJson` **全量重写** + 防抖 500ms
- **触发频率**：**每个文件操作 PRESENT 事件**（工具读/写/编辑都触发）——全仓库最高频写触发之一
- **状态大小**：每会话 { known: {path→firstSeen}, counts: {path→{read,create,modify}}, recent ≤5 }；**known/counts 字典无上限**——长会话触及文件种类 N，状态随 N 线性增长（每个 path 3 个计数对象 + known 条目）
- **写放大估算**：触及 3000 文件 ≈ 每会话镜像 ~500KB-1MB；每次文件事件全量重写 → 高频触发下 **每小时 GB 级写入完全可能**（hit 同一路径会持续触发 persistSoon）
- **风险点**：counts 字典无上界（内存无界风险）+ 全量重写无字节护栏 + 高频触发无节流 + 无资源自监测
- **注意**：本插件当前未在 production profile 启用（候选区），但作为高频写路径样板必须审计

### 3.4 dsh-shared 原语 — 低风险但缺默认护栏

- `jsonlAppender`（`lib/jsonl.js`）：增量 append + 防抖 + compact 回调 + stats。**正确原语，可复用** ✅
- `atomicWriteJson`（`lib/persist.js`）：全量快照原语 + 可选护栏（`minIntervalMs`/`maxBytes`）。⚠️ 默认无护栏（`Infinity`/`0`），调用方不传即裸奔——**建议默认值收紧**（如 maxBytes 默认 1MB + minIntervalMs 默认 1000），或文档强制声明

## 4. resource-budget-review 五维评审的不足

对照 [skill](../../skills/resource-budget-review/SKILL.md) 现状，五维评审已有框架（IO 写入量/写放大倍数/CPU/内存/网络/磁盘存量 + 三遍校验 + 快速检查清单 + 无工具兜底），**缺口**：

| #   | 缺口                                    | 影响                                    | 本 PR 对策                                                     |
| --- | --------------------------------------- | --------------------------------------- | -------------------------------------------------------------- |
| 1   | 无「自动降级」机制模板（只评审不动作）  | #126 缺口 3：资源失控只能人工介入       | 规范 §2.3 降级模板 + observability 落地（资源看门狗降级）      |
| 2   | 无「字节上限」强制（原语默认 Infinity） | 全量重写路径可无护栏                    | 规范 §2.2 模板要求显式 maxBytes + §6 整改项（shared 默认建议） |
| 3   | 无 CI 资源回归门禁                      | #126 缺口 2：发版前无法发现高频路径膨胀 | 本 PR 落 CI 资源冒烟 job                                       |
| 4   | 无「资源曲线平稳」验证入口              | skill 运行期要求未进 verification 模板  | 规范 §5 三遍校验 + 建议 verification 模板加项（见整改表）      |
| 5   | 无「长会话压测」测试形态                | 短会话单测覆盖不到生产形态              | CI 冒烟脚本模拟 1 万+ 事件长会话（见 §5.3）                    |
| 6   | 无高频插件热点清单                      | 新手开发者不知哪些路径高危              | 本文 §3                                                        |

## 5. 分级整改建议表

> 优先级：P0（生产实例事故级风险）> P1（高频路径显著风险）> P2（规范性收尾）。

| 插件/模块            | 风险级           | 整改项                                                                                                                                                                                                                              | 建议优先级 | 状态          |
| -------------------- | ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------- | ------------- |
| dsh-my-observability | 低（已修复核心） | **资源看门狗降级**：写入速率连续 ≥3 次采样超限 → 停止落盘（内存有界，事件仍记录）；连续 ≥3 次正常 → 全量快照恢复落盘。降级/恢复日志 + 面板告警                                                                                      | **P0**     | ✅ 本 PR 落地 |
| dsh-my-observability | 低               | CI 资源冒烟 job（长会话 1 万+ 事件：写放大 ≤1.6 + 降级触发 + 内存有界断言）                                                                                                                                                         | **P1**     | ✅ 本 PR 落地 |
| dsh-my-context       | 中               | ① `atomicWriteJson` 传 `minIntervalMs`（如 ≥1000）+ `maxBytes`（如 512KB）护栏；② **会话数上限**（如 200，FIFO 淘汰最旧会话）或按会话活跃度轮转；③ 可选：usage 汇总与 requests 分离存储（requests 走 jsonl append，汇总走低频快照） | P1         | 📋 建议       |
| dsh-file-activity    | 中-高            | ① **counts/known 字典上限**（如每会话 500 路径，超限 LRU 淘汰最旧 path 或整桶轮转）；② `atomicWriteJson` 护栏参数显式传；③ 写放大复现测试；④ 低频汇总（counts 仅每 30s 快照一次，recent 走增量）                                    | P1         | 📋 建议       |
| dsh-shared           | 低               | ① `atomicWriteJson` 默认 `maxBytes` 收紧（建议 1MB）+ `minIntervalMs` 默认 ≥1000，调用方可覆盖；② persist.js 注释/README 强调「事件流型禁止用快照原语」                                                                             | P2         | 📋 建议       |
| verification 模板    | 低               | 功能级验证清单模板加「资源曲线平稳」项（观察 ≥30 分钟：写入 <100MB、CPU <10%、内存无线性增长）                                                                                                                                      | P2         | 📋 建议       |
